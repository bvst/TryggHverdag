# 9 · Development workflow & progress tracking

**Status:** ✅ Done · **Last updated:** 2026-09-20

## Summary
- **Unit of work:** one requirement ID. "Done" means all of DOD-01 to DOD-08,
  and progress is generated from the tests on `main`.
- **Daily report (D-050):** posted every morning as a comment on a pinned
  "Daily status" issue, so it reaches the owner's phone. `/status` is available
  on demand.
- **Questions while the owner is away (D-051):** one GitHub issue per question,
  labelled `owner-question`, each with a recommendation. The owner answers in
  the issue; `plan-keeper` records the decision.
- **One feature at a time to start (D-052).** Revisit after milestone M2.
- The owner can start and steer sessions from the phone with Remote Control; the
  computer running the sessions must stay on.

## Goal of this section
- How work flows day to day.
- How the owner steers, answers and approves — from a phone, without reading
  code.
- How progress is measured objectively: by tests and checks, not by claims.

## Research findings — round 1

### 1. The owner can run and steer Claude Code from a phone
- With Remote Control, a session started on the computer can be continued from
  the Claude app on a phone. Claude keeps running on the owner's machine.
  Source: https://gigazine.net/gsc_news/en/20260225-claude-code-remote-control
- Since August 2026, a session can also be started from the phone: any computer
  running `claude remote-control` shows up as a device card in the app's Code
  tab.
  Source: https://pasqualepillitteri.it/news/12248/claude-code-avvia-sessione-dal-telefono
- The session keeps its full local environment: files, CLAUDE.md, skills and
  MCP servers.
  Source: https://claudefa.st/blog/guide/development/remote-control-guide
- If the computer sleeps or loses its network, the session reconnects, but
  closing the terminal ends Remote Control.
  Source: https://gigazine.net/gsc_news/en/20260225-claude-code-remote-control
- **Implication:** Every hook and gate from Section 7 stays active even when the
  owner works entirely from the phone. The computer running the sessions must
  stay on.

### 2. Progress can be measured, not reported
- The requirement coverage report (RG-01), the CI checks (Section 8) and the
  canary (REL-10) already produce objective signals. This section turns them
  into a status for each requirement and a report for the owner.

## Definition of Done (proposed)
A requirement is **done** only when all of these are true:

| ID | Condition |
|----|-----------|
| DOD-01 | `docs/specs/<ID>.md` exists, with numbered acceptance criteria |
| DOD-02 | Every acceptance criterion has a test named with its ID, and the pull request shows it failed before the code existed |
| DOD-03 | Every required CI check is green (CI-01 to CI-11) |
| DOD-04 | The blocking reviewers passed, or the owner's override is logged |
| DOD-05 | Mutation score ≥ 80 % on changed safety code (D-036) |
| DOD-06 | A progress entry and the requirement status are updated; new decisions are recorded |
| DOD-07 | The owner approved, if CODEOWNERS paths changed (D-042) |
| DOD-08 | Merged, deployed to staging, and the staging canary is green afterwards |

## Requirement status
Every requirement moves through these states. The status file is generated by
CI from the tests on `main` — nobody edits it by hand.

⚪ not started → 📝 spec written → 🔴 tests written (failing) → 🟢 done (all DoD
met) → 📱 verified on real phones (once L9 runs, D-041) → 🚀 released

File: `docs/requirements-status.md` (generated).

## Owner touchpoints — all possible from a phone

| When | What the owner does | Where |
|------|--------------------|-------|
| Starting or steering work | Start a session, pick the next milestone, answer mid-session | Claude app (Remote Control) |
| Claude needs a decision while the owner is away | Answer one question, which comes with a recommendation | See round 1, question 2 |
| Safety-path or gate changes | Approve based on the plain-language summary | GitHub mobile app |
| Release | Approve the release pull request | GitHub mobile app |
| Weekly | Read the status report | See round 1, question 1 |
| The safety system is down | Get paged | Healthchecks.io and UptimeRobot alerts |

## Session protocol
1. **Start:** the session-start hook shows the plan status, owner to-dos,
   failing gates and open pull requests.
2. **Pick** the next requirement ID in roadmap order (Section 10).
3. **Build** with `/feature <ID>` (or `/bugfix`).
4. **Finish:** progress is updated, the pull request is open, and the stop gate
   passes. Anything unfinished is written to `docs/progress.md` under "In
   flight", so the next session can pick it up.

## Progress metrics (in `/status` and the weekly report)
- Must requirements per milestone: done, verified on phones, total (burn-up).
- CI health: how often `main` is green, and flaky tests.
- Mutation score trend on safety code.
- Canary: success rate and alert time against the REL targets.
- Lead time per requirement.
- Monthly running cost against budget (D-048).
- Open owner questions and to-dos.

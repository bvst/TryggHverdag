#### SM-01 so far, in plain language

The spec is [`specs/SM-01.md`](../specs/SM-01.md), commit `7101f94`. It has 16
acceptance criteria. It delivers SM-01's first sentence (one active journey per
walker), SM-02's start rule (at least one responder to start) and SEC-07 (every
request from a known device) for every route that exists.

What the code does now (`cbc0eeb`):
- **The state machine** lives in one module, `domain/journey.ts`: the states,
  the events (only "start" so far) and a total transition function.
- **`POST /v1/journeys`** starts a journey. The walker is the device's own
  user; the request has no field that could name anyone else. It answers `409`
  when the walker already has an unended journey (and carries that journey's

  a bad body.
- **The database enforces the one-journey rule,** with a partial unique index
  on "not ended". The domain decides, the database makes it true even when two
  requests race. A journey and its responders are written in one transaction.
  The migration was generated by drizzle-kit.

  SHA-256 hash is stored or bound. A store failure while checking it is a `500`,
  never a `401`. No route issues a credential before GRP-01, so staging's
  journey API answers `401` to everyone.

#### D-091 — devices authenticate with a hashed credential until login arrives

Delegated to Claude (D-031), recorded as D-091. Source: SM-01's spec, approach
items 5 and 6.
- A random 32-byte secret per device, base64url, sent as `Authorization: Bearer`.
- Only its SHA-256 hash is stored, in `devices.credential_hash` (unique). The
  device is looked up by that hash.
- One middleware on every route but `GET /v1/health`. The default is closed.
  SM-01-AC9 lists the contract's routes, and since review loop 1 a second test
  pins that the app registers no route outside the contract.
- The same `401` for every cause. A store failure while checking is a `500`. The
  raw header is not passed on to handlers.

**Why not Better Auth's sessions now** (D-032 stands; this only says when):
nothing can sign in until GRP-01; its schema would fix the shape of personal
data before the login task designs the people tables; native heartbeat uploads
need a plain header; and fewer dependencies (SEC-06). **Why plain SHA-256:** a
256-bit random secret cannot be guessed offline, so a slow hash only slows every
request. `privacy-security-reviewer` agreed on 2026-10-01.

**What GRP-01 inherits and decides.** It inherits `users`, `devices`, the port,
the middleware, the public-route tests and the `401` contract. It decides
issuance, expiry, rotation, revocation, the new-device notice, and whether
Better Auth can use UUID user IDs. **The issuer must use `crypto.randomBytes(32)`,
with a test asserting it,** because the plain-SHA-256 argument rests on those 256
bits. The canary's credential (task 8) never expires and is revoked only by
deleting its row. It goes in the secrets inventory and the `staging`
environment.

#### The one question SM-01 left for M4

SM-01's spec asks how long journey records are kept: who walked, when, in which
state, and who followed. The retention rule sets times for positions (24 hours
after a journey ends), alert records (30 days) and account data (when a member
leaves). It sets none for the journey row. Nothing personal waits on the answer
in M2: no journey can end before task 4, and before login none is linked to a
person. **The recommendation:** delete a journey and its responder rows with its
alert records, 30 days after it ends. It is written in `plan/README.md` under
"Open for M4" and in M4's roadmap row. M4 decides it and writes it into the DPIA.

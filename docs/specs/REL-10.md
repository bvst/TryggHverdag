## Summary

- **Where it runs:** inside the worker, as a Graphile Worker cron task every
  15 minutes (`*/15 * * * *`), the place the plan's architecture and the L8
  row already give it. Not a scheduled GitHub workflow (GitHub starts those
  hours late, D-080) and not a separate process (the DEV database's five
  connections have no room for a third pool).
- **What it drives:** the real alert path, through the public staging API,
  with its own device credential: it starts a journey as a fixed test walker
  naming one fixed test responder, sends one heartbeat with no position, goes
  silent, and waits for the watchdog to open the alert and the push sender to
  hand the test responder's lost-contact message to the push port. Then it
  ends the journey with "I'm home" (D-110), well before the two-minute SMS, and
  checks the stand-down is handed over too.
- **What "alerted in time" means in M2 (Q1):** the push port answered the test
  responder's lost-contact message within the five-minute threshold plus 60 s
  of the walker's last contact, by the database's clock. Push and SMS are not
  configured on staging (`NOT_CONFIGURED`), so **the canary does not prove that
  anything reaches a phone**; it proves the server half of the alert path:
  API, journey, watchdog, transaction, outbox and delivery loop.
- **How the owner is paged:** a fourth Healthchecks.io check, `staging-canary`,
  that the owner creates (A-34): a success ping after each passing run, the
  `/fail` signal after each failing one, which pages at once, and silence if
  the canary stops, which pages after the period and grace (Q3).
- **Identities without logins:** fixed, committed IDs for the test walker, the
  test responder and the walker's device. The worker registers them at start;
  the credential is generated by Terraform and lives only in Terraform's state
  and the app's environment. The responder has no device, so nothing can ever
  reach a phone at the critical level (D-087's flag).
- **Cost:** none in money; on the Nano, one journey every 15 minutes, about
  40 short reads per run on the worker's existing pool, and about a thousand
  log lines a day.
- **The exit:** 24 hours of `staging-canary` with no failure and no down event,
  read by the owner from the check's log (A-35), with one `canary_run` line per
  run in Clever Cloud's log.

### How this spec reads its scope

1. **Staging, not production.** REL-10 says "in production"; production does
   not exist until go-live (D-046), and D-090 and the roadmap give M2 the
   staging canary. This task builds the canary so that production runs the
   same code with its own settings at M5; it does not build production's.
2. **"Alert a test responder" in M2 is "the push port answered for the test
   responder".** M2 has no push or SMS provider: the worker's push and SMS
   answer `NOT_CONFIGURED` to every message (`worker.ts`). What the canary can
   observe, and what it cannot, is **Q1**.
3. **"In time" is the reliability target's number:** the five-minute threshold
   (D-021) plus 60 s, counted from the walker's last contact, by the
   database's clock (the server-clock rule; AR-03). The canary gives up waiting
   at that point, so a late alert and a missed one look the same to it: both
   fail the run (approach item 6).
4. **"If not, the owner is alerted immediately"** is Healthchecks.io's failure
   signal, sent at the end of the failing run, which pages at once. A canary
   that stops running cannot send anything; its check pages after its period
   and grace (**Q3**).
5. **"Paging the owner if late"** (D-090) is read as both: a run whose alert
   was late, and a run that did not happen on time.

### What exists today, and what does not

Read on 2026-10-09, in the files themselves:

- **The worker** (`apps/server/src/worker.ts`) runs three in-process loops
  (sweep, push delivery, SMS delivery) every 10 s, and two Graphile cron tasks
  each minute (`HEARTBEAT_CRONTAB`: `heartbeat`, `sms_check`), with Graphile
  concurrency 2 on a pool of 2. Its header says the delivery loop "pages
  nobody until the canary task checks that its test responder was pushed to".
- **Push and SMS** are `UNCONFIGURED_PUSH` and `UNCONFIGURED_SMS`: every
  message is answered `NOT_CONFIGURED`, marked with `last_failure` and retried
  at 10 s, doubling to 60 s, until withdrawn or sent. A message's row records
  `attempts`, `sent_at`, `last_failure` and `withdrawn_at`, but not when it was
  first handed over.
- **Healthchecks.io:** `adapters/healthchecks.ts` sends one HEAD, no body, to
  the ping URL or its `/fail` address; `config.ts` reads two ping URLs by one
  rule; Terraform requires both, validated and different.
- **Nothing on staging can make a credential.** `adapters/device-credentials.ts`
  only checks one; the start task's AC13 tests pin it, and a freshly migrated
  database holds no user and no device. So staging's journey API answers 401
  to everyone.
- **The routes** a canary needs exist: start (`POST /v1/journeys`), heartbeat
  (`POST /v1/heartbeats`, a position optional) and "I'm home" (`POST
  /v1/journeys/{journeyId}/home`). There is no route that reads an alert
  (D-106), so **nothing outside the database can see whether an alert
  opened**.
- **No canary, no canary setting, no `staging-canary` check.** Healthchecks.io
  has three checks: `daily-status`, `staging-worker`, `staging-sms`.

## Approach (technical choices delegated to Claude, D-031)

1. **Where it runs: in the worker, on Graphile Worker's cron.**
   - The worker gains a third cron line, `*/15 * * * * canary ?max=1`, added
     to the crontab only when the canary's own check can be reported to (item
     9). `HEARTBEAT_CRONTAB` stays as it is; the canary's line is a constant of
     its own, appended.
   - **Why the worker:** the architecture's layout already lists the canary
     among `worker.ts`'s jobs, and L8 says "Worker plus external monitor". It
     needs the database to see the alert (no route reads one, D-106), and it
     needs no connection of its own.
   - **Why Graphile's cron, not a fourth in-process loop:** Graphile records
     each cron slot in the database, so during a deploy, when the old and the
     new worker both run for up to a minute or more (D-077 item 13), a slot
     runs once, not twice. **Verified on settling** (2026-10-10, D-128), from
     Graphile Worker 0.18.0's own code in `node_modules`: the job is added
     only for the worker whose upsert into `_private_known_crontabs`
     advances `last_execution` (`dist/cron.js`: the `locks` CTE with `where
     known_crontabs.last_execution < excluded.last_execution`, then `inner
     join locks`), so the second worker adds none. Item 7's rule stays as
     defence in depth.
   - **The task never rejects**, like `sms_check`, so Graphile never retries
     it. `?max=1` says so too, and it is a real crontab option, **verified on
     settling** (D-128): `max`, matched by `CRONTAB_OPTIONS_MAX =
     /^([0-9]+)$/` in `dist/cronConstants.js` and parsed in `dist/crontab.js`,
     where it sets `maxAttempts`. A run is bounded by `CANARY_RUN_LIMIT_MS`, 10
     minutes, inside the 15.
   - **It holds no connection while it waits**, and it is one Graphile job:
     with concurrency 2, the minute check-in and the SMS check share the other
     slot while a run is in flight, each taking under a second (at most 10 s
     against a Healthchecks.io that does not answer). Concurrency is
     unchanged.
   - **It shares nothing with the beat.** A failing canary never stops the
     worker's check-in, and a failing watchdog shows on the worker's own check
     as before (D-115's reason: two faults, two pages).
   - **Rejected:** a scheduled GitHub workflow (GitHub started the daily
     report about 4¾ hours late, D-080; its logs are kept outside the EEA; and
     it could not see the alert without a new read route); a separate process
     on the instance (a third pool, past the DEV plan's five connections at a
     deploy); Healthchecks.io alone (it runs nothing; it is the pager).

2. **What a run does, in order.** Each step's failure is named (item 6), and
   the journey, once started, is always ended.
   1. **Registration** (item 4), once per process; again on each run until it
      has succeeded.
   2. **Start:** `POST /v1/journeys` with `{ "responderIds": [CANARY_RESPONDER_ID] }`
      through the public API, with the canary's credential. A 409
      `ALREADY_ON_A_JOURNEY` is item 7.
   3. **One heartbeat:** `POST /v1/heartbeats` with the journey's ID, a fresh
      event ID, `batteryLevel: null` and `position: null`. Then the journey is
      read: its `last_heartbeat_at` must be set. That time is **last contact**.
   4. **Silence:** the run waits until last contact + `CANARY_FIRST_LOOK_MS`
      (290 s), the wait's length worked out from the database's `now()`.
   5. **Watching:** every `CANARY_POLL_MS` (2 s) one read: the database's
      `now()`, the journey's alert if one has opened, and whether the push
      port has answered the test responder's `LOST_CONTACT` message of that
      alert (`sent_at` or `last_failure` set). It stops at the first read that
      sees an answer, or the first whose `now()` is past last contact +
      `CANARY_DEADLINE_MS`.
   6. **"I'm home":** `POST /v1/journeys/{journeyId}/home`, whatever step 5
      found. A 200 is expected; a 409 `JOURNEY_ENDED` means something else
      ended it (`HOME_FAILED`).
   7. **After:** one read: the journey `ENDED`, end reason `HOME`; the alert,
      if one opened, `RESOLVED`, resolution `HOME`; and no `LOST_CONTACT_SMS`
      written for it.
   8. **The stand-down:** if an alert opened, reads every 2 s until the push
      port has answered the test responder's `HOME` stand-down, at most
      `CANARY_STAND_DOWN_LIMIT_MS` (90 s) after the alert's `resolved_at`. Why
      90: a stand-down is due at once, or at most 60 s on when it is held
      behind a withdrawn message still in a port's hands (D-112), plus one
      delivery interval and a margin.
   9. **The outcome** is the first failure in this order, or `ON_TIME`. One
      `canary_run` line; then the report (item 9).
   - A full passing run takes about 5½ minutes, a failing one at most about
     7½. The canary ends its journey at the latest at last contact + 360 s
     and a request's time, and an alert opens no earlier than last contact +
     300 s, so it escalates no earlier than + 420 s: the canary's journey is
     always ended at least about 55 s before its alert could escalate.

3. **Through the public API, not in-process.** The client calls
   `CANARY_API_URL` (on staging `https://trygg-hverdag-staging.cleverapps.io`),
   so the canary goes through Clever Cloud's routing, TLS, the API process,
   its authentication, the contract's validation and its routes, as a phone
   would.
   - **`adapters/canary.ts`'s client** uses Node's `fetch` and the contract's
     own schemas for each route's path, request and answer (no new
     dependency: the dependency rule's "keep dependencies few"). Each request has its own
     10 s timeout, `redirect: 'manual'` (a 3xx fails, naming its status), and
     sends the credential only as `Authorization: Bearer` to the configured
     origin. Its errors are new errors built from words chosen there, as
     `healthchecks.ts`'s are, so no credential reaches a log.
   - The heartbeat's event ID is made in the adapter (`crypto.randomUUID()`),
     so the module stays free of randomness.
   - **Rejected:** calling the journey module in-process. It skips the API, the
     authentication and the contract, which a bad release can break too (F8).

4. **The canary's identities, and its credential.**
   - **Three fixed IDs**, chosen once by the implementer as random lower-case
     v4 UUIDs, committed in `domain/canary.ts` and pinned by a test:
     `CANARY_WALKER_ID`, `CANARY_RESPONDER_ID` and `CANARY_DEVICE_ID`. They are
     what tells the canary's rows apart from every other: `users` holds only
     an ID, so a flag column would add a schema change for what an ID already
     says. Nothing about them is personal (RG-07; the repository is public,
     D-089).
   - **Registration** (`registerCanary`, in `adapters/canary.ts`), one
     transaction: both users inserted if absent (`on conflict do nothing`);
     the walker's device inserted with the SHA-256 of the canary's credential,
     or, if it exists, its hash replaced, which is how a rotated credential
     takes effect. A device with the canary's ID that belongs to anyone but
     the canary's walker is refused with a throw (`REGISTER_FAILED`). The
     responder gets **no device**.
   - **The credential** is 43 characters of letters and digits (about 256
     bits, D-091's strength) generated by Terraform's `random_password`
     (`length = 43`, `special = false`, marked sensitive), passed to the app
     as `CANARY_CREDENTIAL`. It is therefore in Terraform's state in Cellar
     and in the app's environment on Clever Cloud, as the database password
     already is (D-077), and **in no GitHub secret and no owner's hands**.
     Rotating it is a Terraform replace of that one resource, then a plan and
     apply; the worker's registration replaces the hash at its restart.
   - **Why a stable credential and not one made by each worker at start:** the
     "I'm home" route admits only the device that started the journey
     (D-110), so a worker restarted mid-run, or the new worker of a deploy,
     must be the same device to end a journey the old one left. A per-process
     credential would also cut off the old worker's run in a deploy (401), and
     each of those would page.
   - **This is the one exception to D-091's "no insert function creates a
     credential"**, which D-090's "on staging, from the canary" asks for. It
     is held narrow: only `worker.ts` may import `adapters/canary.ts` (an
     import rule beside D-108's), the registration writes only the three fixed
     IDs, the API process has no way to reach it, and a freshly migrated
     database still holds no user and no device (the start task's AC13,
     unchanged). `device-credentials.ts`'s header is corrected to say so.
   - **D-087's flag holds by construction in M2:** the responder has no device,
     no push target exists in M2, and nothing is sent. M3's push adapter is
     told (Left for later).

5. **What the canary checks, and from where.** Every decision is made on the
   database's times, read with each observation (the server-clock rule; the
   module reads no clock; the waits are timers, which decide nothing).
   - **The read** (`observeCanaryJourney(journeyId)`, one statement): `now()`;
     the journey's state, `started_at`, `last_heartbeat_at`, end reason, and
     only when its `walker_id` is `CANARY_WALKER_ID` (any other journey reads
     as none); its alert (`opened_at`, state, resolution, `resolved_at`);
     whether the push port answered the responder's `LOST_CONTACT` message
     of it, and its `HOME` stand-down; how many `LOST_CONTACT_SMS` it has. No
     lock, no write.
   - **"Answered" is any answer from the port** (`sent_at` or `last_failure`
     set): in M2 always `NOT_CONFIGURED`. The run line says which (Q1).
   - **The canary changes nothing in the database itself** apart from item 4's
     registration. Its journeys start, beat and end through the API, under the
     API's own rules, with its own credential, so it cannot act on anyone
     else's journey.

6. **The verdict** (`domain/canary.ts`, pure). From last contact, the alert's
   `opened_at` (or none) and the `now()` of the first read that saw the port's
   answer (or none):
   - **`OPENED_EARLY`** when the alert opened less than
     `LOST_CONTACT_AFTER_MS` after last contact: a false alarm, a defect of
     its own (F2).
   - **`NOT_OPENED`** when no alert had opened by the deadline.
   - **`NOT_HANDED_OVER`** when an alert opened but the port had not answered
     by last contact + `CANARY_DEADLINE_MS`, which is
     `LOST_CONTACT_AFTER_MS + ALERT_TIME_SLACK_MS`, 360 000 ms, from the
     domain's own constants. This is the wedged or stopped delivery loop D-108
     left for the canary.
   - **`ON_TIME`** otherwise, with `alertMs` = answered − last contact and
     `openedAfterMs` = opened − last contact.
   - Exactly at the deadline is on time; a millisecond after is not. The
     answer's time is the `now()` of the read that first saw it, so it is
     late by at most one poll, 2 s: a run can fail by up to 2 s early, never
     pass late.
   - The other outcomes come from the steps: `NOT_CONFIGURED`,
     `REGISTER_FAILED`, `START_FAILED`, `HEARTBEAT_FAILED`, `READ_FAILED`,
     `HOME_FAILED`, `NOT_RESOLVED`, `ESCALATED`,
     `STAND_DOWN_NOT_HANDED_OVER`, `RUN_LIMIT`; and `INTERRUPTED` (item 8),
     which is not reported.
   - **`MISSED_ALERT_OUTCOMES`** is `NOT_OPENED` and `NOT_HANDED_OVER`: what
     D-022's "missed canary alert" means for this canary (Q2). It is a list
     the monitoring guide and the run line name; no code decides by it.

7. **Leftovers and overlap.** A walker can have one unended journey, held by
   the database (the start task's unique index). So a start answered 409
   `ALREADY_ON_A_JOURNEY` names the canary's unended journey, and the run
   reads it:
   - started `CANARY_LEFTOVER_AFTER_MS` (10 minutes) or more ago by the
     database's clock: **a leftover** of a run that did not finish (a crash, a
     stop that could not end it). The run ends it through "I'm home" (a 200,
     or a 409 if it ended meanwhile), writes one `canary_leftover_ended` line
     with its ID, and starts again, once. A second 409 is `START_FAILED`.
   - started less than 10 minutes ago: **another run is in flight**, the old
     or the new worker's in a deploy. This run writes one `canary_skipped`
     line, reports nothing, and ends. So two runs never both report, and the
     one in flight is never cut off.
   - A leftover that sat past its alert's two minutes has escalated, and
     `staging-sms` has paged for it: correct, since a run was lost. Ending it
     withdraws its unsent SMS (D-116), which clears that page.

8. **A stop during a run.** The task takes Graphile's abort signal, which
   fires at once on a stop (`gracefulShutdownAbortTimeout: 0`). A run that is
   stopped sends "I'm home" for its journey once, bounded by
   `CANARY_STOP_LIMIT_MS` (5 s) of its own, writes `canary_run` with
   `INTERRUPTED`, and reports nothing. A stop therefore waits at most 5 s
   longer than it does today. Whatever it leaves, the next run's item 7 ends.
   A run that reaches `CANARY_RUN_LIMIT_MS` is aborted the same way, but
   reported as a failure (`RUN_LIMIT`).

9. **The page: a check of its own** (`staging-canary`, A-34).
   - `HEALTHCHECKS_CANARY_URL`, read by `config.ts`'s ping-URL rule (D-116:
     `https://`, the host, `/` and a lower-case UUID, nothing else), refused
     unless its UUID differs from both other checks' (the worker's and the SMS
     check's): one green ping must never keep another check green.

     `adapters/healthchecks.ts`, a safety path, is not changed. A report that

     answered Q3 (D-127). The failure signal pages at once; a canary that stops

     says so at start, naming what goes unpaged; on staging Terraform refuses

    - **Synthetic by construction:** no name, no phone number, no position,

      about 580 rows a day, about 17 000 a month, a few megabytes against the

## Acceptance criteria

The canary C runs against the real API, the journey store (the fake at L6, the
adapter at L3), the watchdog, the push sender with the recording push fake
(answering `NOT_CONFIGURED`, as the worker's push does), the SMS sender with
the recording SMS fake, and a recording alarm, on a controlled clock, unless a
criterion says otherwise. "A run" is one call of the canary's task. W, R and D
are `CANARY_WALKER_ID`, `CANARY_RESPONDER_ID` and `CANARY_DEVICE_ID`.

### The run

**REL-10-AC1 — A healthy system: the alert reaches the push port in time, the
journey ends, the stand-down follows, and the canary reports `ok`.** *(Q1 (a))*
- **Given** the loops healthy and C registered
- **When** a run runs
- **Then** it starts one journey J through `POST /v1/journeys` with D's
  credential, naming R alone; sends one heartbeat with no position and no
  battery level; and J's `last_heartbeat_at` is set
- **And** the watchdog opens J's alert A no earlier than last contact + 300 s;
  the push fake receives R's `LOST_CONTACT` message for A, with exactly
  `messageId`, `recipientId` and `kind`; C sees the port's answer by last
  contact + 360 s
- **And** C sends "I'm home" for J (200); J is `ENDED`, `HOME`; A is
  `RESOLVED`, `HOME`; the push fake receives R's `HOME` stand-down within
  90 s of A's `resolved_at`
- **And** the alarm receives exactly one `ok`; one `canary_run` line,
  `ON_TIME`, with `alertMs` equal to the answer read's `now()` minus last
  contact and `openedAfterMs` to A's `opened_at` minus last contact
- **And** nothing reaches the SMS fake; no message is written to W.

**REL-10-AC2 — The watchdog does not open the alert: `NOT_OPENED`, paged at
once.**
- **Given** the sweep loop not running (and, in another case, every sweep
  failing)
- **When** a run runs
- **Then** at the first read past last contact + 360 s C stops waiting, sends
  "I'm home" (200, J `ENDED`, `HOME`, no alert), the alarm receives exactly
  one `failing`, and `canary_run` says `NOT_OPENED`
- **And** C's run is over no later than last contact + 360 s plus its last
  poll and the request.

**REL-10-AC3 — The alert opens but never reaches the push port:
`NOT_HANDED_OVER`. D-108's unwatched delivery loop is watched.** *(Q1 (a))*
- **Given** the sweep healthy, and in turn: the delivery loop not running; the
  push port holding every answer (the fake's `holdAnswers`); the claim
  failing every time
- **When** a run runs
- **Then** A opens, C sees no answer by last contact + 360 s, sends "I'm home"
  (A `RESOLVED`, `HOME`, R's unsent lost-contact message withdrawn), and
  reports `failing` once; `canary_run` says `NOT_HANDED_OVER` with
  `openedAfterMs` set
- **And** an answer read at exactly last contact + 360 000 ms is `ON_TIME`;
  one first read at + 360 001 ms is `NOT_HANDED_OVER`.

**REL-10-AC4 — An alert that opens early is a failure of its own:
`OPENED_EARLY`.**
- **Given** a sweep that opens J's alert at last contact + 4 minutes (a stub
  watchdog, as the sweep tests stub the store)
- **When** a run runs
- **Then** at its first look C reports `failing` once with `OPENED_EARLY`, and
  ends J
- **And** when the opening comes at exactly + 300 000 ms it is not early.

**REL-10-AC5 — The verdict is a pure rule on the database's times.**
- **Then** `alertVerdict` gives, for any last contact, opening and answer
  (fast-check): `OPENED_EARLY` exactly when the opening is less than
  `LOST_CONTACT_AFTER_MS` after last contact; else `NOT_OPENED` when there is
  no opening; else `NOT_HANDED_OVER` when there is no answer or it is more
  than `CANARY_DEADLINE_MS` after last contact; else `ON_TIME` with both
  durations; never a throw; nothing handed in changed
- **And** `CANARY_DEADLINE_MS` is `LOST_CONTACT_AFTER_MS +
  ALERT_TIME_SLACK_MS` and 360 000; each other constant is the interfaces'
  value; `CANARY_FIRST_LOOK_MS` is under `LOST_CONTACT_AFTER_MS`; the run
  limit is under 15 minutes and above the longest run (deadline, stand-down
  limit, three request timeouts); the deadline plus a request timeout is
  under `LOST_CONTACT_AFTER_MS + ESCALATE_AFTER_MS`, so C always ends its
  journey before its alert could escalate
- **And** `reportFor` is `ok` for `ON_TIME`, null for `INTERRUPTED`, `failing`
  for every other outcome; `CANARY_OUTCOMES` and `MISSED_ALERT_OUTCOMES` are
  exactly the interfaces' lists
- **And** the domain and the module read no clock (the lint rule).

**REL-10-AC6 — Every step fails loudly, and the journey is still ended.**
- **Given**, in turn: the start answered 401, 422, 500, a 3xx, a body the
  contract refuses, a network failure, and no answer within 10 s; the
  heartbeat answered 500, or 2xx with `last_heartbeat_at` left null (a store
  stub); "I'm home" answered 500, or 409; after "I'm home", J not `ENDED`
  `HOME` or A not `RESOLVED` `HOME` (a store stub); R's `HOME` stand-down
  never answered (the push port holding answers after the alert); any read
  failing with a SQLSTATE
- **Then** the outcome is, in order, `START_FAILED`, `HEARTBEAT_FAILED`,
  `HOME_FAILED`, `NOT_RESOLVED`, `STAND_DOWN_NOT_HANDED_OVER`, `READ_FAILED`;
  the alarm receives exactly one `failing`; `canary_run` carries the HTTP
  status or the SQLSTATE, and null for the other
- **And** whenever J was started, "I'm home" is sent for it once before the
  run ends, whatever failed after
- **And** when two steps fail, the outcome is the earlier one.

**REL-10-AC7 — The canary never escalates and never pages through the SMS
check.**
- **Given** the loops healthy and the SMS check reporting to its own recording
  alarm
- **When** C's task runs every 15 minutes for 24 hours of the fake clock (96
  runs)
- **Then** all 96 are `ON_TIME`; no `LOST_CONTACT_SMS` is written for any
  canary alert; every canary journey is `ENDED`, `HOME`, before its alert's
  `opened_at` + `ESCALATE_AFTER_MS`; the SMS check reports `ok` every minute;
  the 24-hour end never touches a canary journey
- **And** when an alert escalates anyway (an escalation stubbed to run at
  once), the run's outcome is `ESCALATED`, unless an earlier outcome applies.

**REL-10-AC8 — A leftover is ended first; a run in flight is never cut off;
two runs never both report.**
- **Given** an unended canary journey started 10 minutes or more ago by the
  database's clock, `ACTIVE` and, in another case, `LOST_CONTACT` with its
  alert escalated
- **When** a run runs
- **Then** its start meets 409, it ends that journey through "I'm home" (a 409
  there accepted too), writes one `canary_leftover_ended` line with that
  journey's ID, starts again once and runs as AC1; the leftover's unsent SMS
  are withdrawn
- **And given** an unended canary journey started under 10 minutes ago, the
  run writes one `canary_skipped` line, ends nothing, sends nothing, and
  reports nothing
- **And** with two runs started together on one store (L6) and on one
  database (L3), exactly one runs a journey and reports; the walker never has
  two unended journeys; a second 409 after ending a leftover is
  `START_FAILED`.

**REL-10-AC9 — A stop or the run limit ends the run quickly, and only the run
limit is reported.**
- **Given** a run waiting for its alert
- **When** the worker stops (Graphile's abort signal)
- **Then** the run sends "I'm home" for J once, waits for it at most
  `CANARY_STOP_LIMIT_MS`, writes `canary_run` with `INTERRUPTED`, reports
  nothing, and the worker's stop finishes no more than 5 s later than without
  a run
- **And when** a run is still going at `CANARY_RUN_LIMIT_MS` (a client that
  never answers, whose own timeout is lifted in the test), it is aborted, ends
  J the same way, and reports `failing` with `RUN_LIMIT`
- **And** the task never rejects, in any of the cases of AC2 to AC9, so
  Graphile never retries it.

- **And** a freshly migrated database still has no user and no device (the

  health still answers 401 (unchanged)
- **And** only `worker.ts` and tests import `adapters/canary.ts`, and only the
  worker process calls `registerCanary` (an import rule with its tests,

**REL-10-AC11 — The canary reads only its own journeys, and changes the
database only through the API.**
- **Given** journeys of other walkers in every state and end reason, with
  alerts in every state and messages of every kind (L3; and the fake, L2)
- **Then** `observeCanaryJourney` returns null for each of their IDs, and the

- **And** over AC1's run and AC8's leftover run, every row of every other

- **And** the observation's `now` is the statement's `now()`, and its other

**REL-10-AC12 — The canary's page is its own, and never touches the

- **Given** the worker started with all three ping URLs set and different
- **Then** an `ON_TIME` run reports `ok` to the canary's check only; a failing

- **And** with every canary run failing, the sweep, the beat, the minute

- **And** a report that fails writes one `canary_report_failed` line and
  nothing else.

**REL-10-AC13 — The settings are read, said at start, and never stop the
worker.**
- **Then** `readCanarySetting` takes an `https:` origin with no path, query,
  fragment or credentials, and a credential of 43 or more base64url
  characters; it refuses every other value with a reason naming the variable
  and not the value (an unset, empty, `http:`, path, query, fragment,
  user-info, non-canonical spelling; a credential too short or with another
  character)
- **And** `HEALTHCHECKS_CANARY_URL` is read by the ping-URL rule, and the
  worker refuses it when its UUID equals the worker's or the SMS check's
- **And** the worker's start lines say whether the canary runs and, when not,
  why and what goes unpaged; no line holds a value
- **And** with the canary's check usable and its other settings not, the
  canary is scheduled and each run reports `failing` with `NOT_CONFIGURED`;
  with the canary's check unusable, no `canary` cron line is added and
  nothing reports
- **And** no combination of these settings stops the worker or changes its
  three loops, its check-in or its SMS check.

## Risks and failure modes

- **[F8](../plan/03-safety-reliability-security.md#failure-modes), a bad
  release breaks alerts: what this task exists for.** After any deploy, the
  next slot's run goes through the API, the watchdog, the outbox and the
  delivery loop; a release that stops any of them fails a run within about
  21 minutes of the deploy and pages at once. **What it does not catch in
  M2,** said plainly:
  - **That anything reaches a phone.** Push and SMS are not configured; the
    canary sees the port's `NOT_CONFIGURED` (Q1).
  - **A provider that fails every send.** In M2 every send "fails" by design,
    so D-108's "always failing" cannot be told from normal (disagreement 6).
  - **The critical level, Time Sensitive, Do Not Disturb**: no push exists.
  - **The SMS escalation, "I'm on it", "They're safe", the 24-hour end, a
    removal**: the canary does none of them; the L6 tests do.
  - **The location path**: the canary sends no position.
  - **More than one responder, or more than one journey at once.**
  - **The phone side**: background survival, a real phone's heartbeats, the
    force-quit reminder (L9).
  - **Production**, which does not exist yet.
- **[F6](../plan/03-safety-reliability-security.md#failure-modes), from the
  canary's side: a canary that says `ok` when it should not.** The verdict is
  pure and property-tested (AC5), each failure has its L6 test (AC2 to AC9),
  and the module is mutation-tested (AC18). A canary that stopped running
  pages through its check's silence (Q3).
- **[F6], the canary interfering with real journeys.** It reads only its
  walker's journeys, acts only through the API with its own credential (which
  the API's rules confine to its own journeys), and deletes nothing (AC11).
  On staging there are no real journeys; in production (M5) this is what
  keeps it harmless.
- **[F7](../plan/03-safety-reliability-security.md#failure-modes), the
  worker down.** The canary lives in the worker, so a dead worker stops it
  too: `staging-worker` pages first, within about three minutes (D-079), and
  `staging-canary` follows. The canary cannot slow the watchdog: no new pool,
  a few reads per run, one Graphile slot; its failures never touch the beat
  (AC12).
- **[F2](../plan/03-safety-reliability-security.md#failure-modes), false
  alarms, here false pages.** A page that is wrong teaches the owner to ignore
  the right one (D-080's lesson). Held by: the skip rule in a deploy (AC8),
  `INTERRUPTED` not reported (AC9), the grace tolerating one lost run (Q3),
  the deadline's margin of about 40 s (item 12), and polling that can only
  fail early by 2 s, never pass late. **Left:** a Clever Cloud routing blip
  during a run's three requests fails that run and pages; it is a real
  failure for a phone too.
- **Nano's reduced CPU priority** (D-077) could make a run late; the run lines
  measure it (item 12).
- **The credential.** A leaked `CANARY_CREDENTIAL` lets someone start, beat
  and end the canary's journeys on staging, naming only the canary's
  responder: synthetic, no one alerted, and it would show as failing or
  skipped runs. It is in Terraform's state and the app's environment only;
  never logged (AC15); rotated by replacing one Terraform resource.
- **The exception to "nothing makes a credential"** (D-091) is held by an
  import rule, fixed IDs and the API having no path to it (AC10). The login
  task must keep it so (Left for later).
- **Growth until retention.** About 580 rows a day; the claim's index gains
  about 190 unsent rows a day (item 11). Small for months; M4 must cover it.
- **Healthchecks.io itself.** A report that cannot reach it is a line; the
  check then goes late and down, a false page. Accepted, as for the other
  checks.
- **[F1](../plan/03-safety-reliability-security.md#failure-modes),
  [F3](../plan/03-safety-reliability-security.md#failure-modes),
  [F4](../plan/03-safety-reliability-security.md#failure-modes),
  [F5](../plan/03-safety-reliability-security.md#failure-modes),
  [F9](../plan/03-safety-reliability-security.md#failure-modes),
  [F10](../plan/03-safety-reliability-security.md#failure-modes):** not
  touched; all are the phone's side.

### Q1 — In M2, what counts as "the system alerted the test responder in time"?

**Answered: (a)** (the owner, 2026-10-10; D-127).

**Why it is asked.** REL-10 asks that a test responder be alerted in time,
and M2's exit is "the staging canary alerts on time for 24 hours". Staging
has no push or SMS provider until M3: every message is answered
`NOT_CONFIGURED`. What M2's canary proves, and so what M2's exit means, is a
scope choice.

**Options:**
- **(a) The push port answered the test responder's lost-contact message
  within five minutes plus 60 s of last contact.** It proves the server half
  of the path (the API, the journey, the watchdog, the transaction, the
  outbox, the delivery loop) on every run, and catches a stopped or wedged
  delivery loop, the gap D-108 left. It does not prove that anything reaches
  a phone, or that a provider works. M3 tightens it to "accepted" once the
  canary has a push target.
- **(b) A stand-in push for the canary only,** which accepts the canary's
  messages so they count as sent. Rejected by Claude: it puts a branch in the
  production push path that marks messages sent without sending them; one
  wrong match there is a real alert counted as sent and never delivered.
- **(c) In M2, only that the alert opened in time;** the push half waits for
  M3. Simpler by one read, but leaves the delivery loop unwatched, which is
  what D-108 asked the canary to close.

**Recommendation: (a).**
- It checks everything that exists in M2, end to end, and nothing it cannot.
- It closes the one unwatched loop (D-108) without touching the push path.
- Its cost: M2's exit means "the alert reaches the push port on time", not
  "a phone is alerted". The spec says so wherever it reports.

**If answered otherwise:**
- **(b):** a canary-only push adapter in `worker.ts`, keyed by
  `CANARY_RESPONDER_ID`, with its own tests that no other recipient ever
  reaches it; AC1 and AC3 read "sent".
- **(c):** AC3 goes; the verdict reads the opening only; D-108's gap stays
  open until M3, said in "Left for later".

### Q2 — Does a missed alert on the staging canary stop feature work (D-022)?

**Answered: (a)** (the owner, 2026-10-10; D-127).

**Why it is asked.** D-022 and the reliability targets say "Any missed canary
alert stops all feature work until it is fixed and covered by a test". That
was written with production's canary in mind; until M5, staging's is the only
canary. Applying it can halt M3's work on a staging fault; not applying it
lets a broken alert path sit while features ship.

**Options:**
- **(a) Yes, for a missed alert as this canary sees it:** the alert did not
  open, or did not reach the push port, by the deadline (`NOT_OPENED`,
  `NOT_HANDED_OVER`). Each gets a BUG and is fixed, with a test, before more
  feature work. Every other failing run (an API step, a stand-down, an early
  alert, the canary's own configuration) pages and gets a BUG, but does not
  stop the line by itself.
- **(b) Yes, for every failing run.**
- **(c) No, not until production;** staging's failures page and get a BUG.

**Recommendation: (a).**
- It is D-022's own word, "missed", read for what this canary can see.
- A failure before the journey existed (the API unreachable) is an outage
  UptimeRobot also sees, not a missed alert; (b) would stop work for it.
- (c) leaves the only end-to-end signal of the safety loop without teeth for
  months.

**If answered otherwise:** no criterion changes; `MISSED_ALERT_OUTCOMES` and
the monitoring guide's "When `staging-canary` pages you" follow the answer
((b): every failure; (c): the list stays, marked "for production").

### Q3 — How long may the canary stop running before you are paged?

**Answered: (a)** (the owner, 2026-10-10; D-127).

**Why it is asked.** A failing run pages at once. A canary that stops running
sends nothing, so only its check's period and grace can page. A deploy or a
worker restart in the middle of a run costs that run (it is not reported), so
a grace that pages at the first lost run pages on some deploys for nothing.

**Options:**
- **(a) Period 15 minutes, Grace 20 minutes: one lost run is tolerated.** A
  stopped canary pages about 35 minutes after its last success. A dead
  worker still pages within about three minutes through `staging-worker`.
- **(b) Period 15 minutes, Grace 5 minutes: the first lost run pages,** about
  20 minutes after the last success. A deploy that lands in the six minutes a
  run takes (about two deploys in five) pages for nothing.

**Recommendation: (a).**
- The case only the grace covers is the worker alive while its canary is not;
  the worker's own death pages within about three minutes either way.
- (b)'s false pages come with merges, several a day in M3, and a page that is
  often wrong teaches the owner to ignore the right one (D-080).

**If answered otherwise:** A-34's grace becomes 5 minutes, and AC19's "at
least one success in every 35 minutes" becomes 20. No code changes.

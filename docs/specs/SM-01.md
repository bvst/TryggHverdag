### Readings this spec makes

Each is stated so the reviewers can check it, not assumed quietly.

1. **"Active" means "not ended".** In the rest of this spec an **unended
   journey** is one in any state but `ENDED`: today `ACTIVE` or
   `LOST_CONTACT`. The rule writes "active" in lower case. D-033 makes
   `ACTIVE` a state name, but a journey in `LOST_CONTACT` is still running:
   its alert is open and its responders are being told. A second journey
   started beside it would split the walker's heartbeats between two
   journeys. The watchdog would then be watching one of them for a silence
   that is really the other's.
2. **A responder is an existing user other than the walker.** The MVP's
   people section defines a responder as "a group member who follows a
   walker's journey and receives alerts", and D-008 says it outright:
   "Responder" = group member. Groups do not exist until the login task, and
   the MVP has one private group (D-004, D-008, D-009), so for now "member"
   means "existing user". If the walker could name themself, SM-02
   would be met by a list that alerts nobody.
3. **"Every request" means every route a device calls.** `/v1/health` stays
   public. It carries no personal data. The monitors that call it (INF-08,
   D-079) and Clever Cloud's deploy check are not devices, and REL-08 depends
   on them reaching it.
4. **"Validates what it receives" means, in this task, the start request.**
   Validating heartbeats is task 2's half.

## Approach (technical choices delegated to Claude, D-031)

1. **The state machine is one module: `apps/server/src/domain/journey.ts`.**
   It holds:
   - the list of states, `JOURNEY_STATES`: D-033's three, `ACTIVE`,
     `LOST_CONTACT` and `ENDED`;
   - the list of event types, `JOURNEY_EVENTS`: `start` only;
   - the transition function, `transition`.

   The types are derived from the two lists (`typeof JOURNEY_STATES[number]`),
   so a list and its type cannot disagree.

   **Declaring all three states now adds no behaviour.** No event in this task
   leads into `LOST_CONTACT` or `ENDED`. Each arrives with the task that
   brings its event (tasks 3, 4 and 7). Declaring them now has two benefits:
   - the database constraint for SM-01 is right the first time (item 3);
   - the tests can show that a walker whose journey is in `LOST_CONTACT`
     still cannot start a second one.

   **How a later task is stopped from adding a state or an event without a
   test:**
   - **L1.** While `start` is the only event, `transition` hands the event
     straight to the start rule, so a second event type added to the event
     union is a type error at that call. When the second event arrives, its
     task brings back a `switch` with `const unhandled: never = event`, and
     the default case throws, never returns (review loop 1: a returned
     fallback would read as a silently skipped outcome once the watchdog
     reads `outcome.type`).
   - **L2.** The transition test holds an expected outcome for every pair of
     (situation, event type). Its table is typed with `satisfies` over the
     module's own lists, so a missing pair is a type error. It also iterates
     the exported lists at run time and fails, naming the pair, for any pair
     it has no expectation for. `implementer` cannot edit tests (RG-02, HK-02),
     so a new state or event cannot pass until `test-author` has written its
     rows.
   - **L3.** The database's set of allowed states is compared with
     `JOURNEY_STATES` (SM-01-AC15). A state added on one side only fails.
   - **Mutation.** `domain/` is a safety path. Its tests, the `domain` group in
     `MUTATION_GROUPS`, must keep the score at 80 % or more (D-036), and
     RG-04's 95 % branch floor applies.

   **The "start" situation** is the walker's unended journey (`{ id, state }`),
   or `null` if there is none. An `ENDED` journey is never a current journey:
   the store never returns one. If one is handed to `transition` anyway, it
   counts as no journey, because `ENDED` frees the walker (review loop 1).
   Blocking instead would answer 409 naming the ended journey, which tells
   the app to adopt a journey nobody watches. So the start table has four
   rows: none, `ACTIVE`, `LOST_CONTACT`, and `ENDED` treated as none. Later
   journey events (heartbeat, from task 2) take the journey they name as their
   situation, and their tables cover all three states.

2. **The start decision, in order** (`transition(current, { type: 'start',
   walkerId, responderIds, existingUserIds })`, where `existingUserIds` is the
   set of the named IDs that exist as users):
   1. The walker has an unended journey → refused, `ALREADY_ON_A_JOURNEY`,
      carrying that journey's ID (SM-01). This comes first whatever the list
      says, so a retried start always learns about the journey it already
      has.
   2. The list names the walker, or an ID that is not an existing user →
      refused, `INVALID_RESPONDER`. The whole start is refused. Dropping the
      bad ID silently would let a walker believe someone is following them
      who is not.
   3. The list is empty → refused, `NO_RESPONDER` (SM-02).
   4. Otherwise → started, state `ACTIVE`, with the distinct responder IDs in
      the order first named. A repeated ID counts once.

   Each outcome is a value (`{ type: 'started', … }` or `{ type: 'refused',
   reason, … }`). None is an exception, and no input makes `transition` throw
   or return `undefined`.

3. **SM-01 is decided by the domain and enforced by the database.**
   - The module reads the walker's unended journey, asks `transition`, and
     writes what it returns.
   - Two starts racing past that read are stopped by a **partial unique
     index**, `journeys (walker_id) WHERE state <> 'ENDED'`. The predicate
     names the one state that frees the walker, not the states that block, so
     a state added later blocks a second journey by default, which is the safe
     direction.
   - The adapter reports a violation of that index as "not inserted", with
     the unended journey's ID read back. The caller then gets the same
     `ALREADY_ON_A_JOURNEY` as in step 1.
   - The journey row and its responder rows are written in **one
     transaction**. A journey without its responders, for even a moment, is a
     journey the watchdog (task 3) would alert nobody about.

4. **Time.** `started_at` comes from the injected `Clock` port
   (`ports.ts`). In the API process that is the database clock (D-065 item 3,
   REL-01). Domain code reads no clock (AR-03, D-067, enforced by the lint
   rule on `domain/`). The module is outside that lint rule's paths, so it
   takes the time from the port too, never from the process.

5. **Device authentication: a minimal per-device credential now, issued
   through Better Auth from the login task on.**
   - **What it is:**
     - A random secret per device: 32 bytes from Node's CSPRNG
       (`node:crypto`), base64url-encoded.
     - The app sends it as `Authorization: Bearer <credential>`.
     - The server keeps only its SHA-256 hash, in `devices.credential_hash`,
       which has a unique index, and looks the device up by that hash.
     - The answer is the device and its user. The walker of any journey this
       device starts is that user, and the request has no field that could
       name anyone else.
   - **Why hashed:** a copy of the database (SEC-03, server breach) then
     holds no working credential. For a 256-bit random secret a plain
     SHA-256 is enough. A slow password hash would only slow every request.
   - **Where:**
     - a port, `DeviceAuthenticator.authenticate(credential)`, which resolves
       to `{ deviceId, userId }`, or `null` for "not a valid credential", and
       rejects when it cannot check;
     - its adapter, `adapters/device-credentials.ts`;
     - a recording fake in the test kit;
     - one oRPC middleware in `api.ts`, applied to the whole router.

     **Health is the only route outside it.** The default is closed: a route
     added later is authenticated unless someone deliberately moves it out,
     and SM-01-AC9's test fails if they do.
   - **Why not Better Auth's session model now** (D-032 keeps Better Auth as
     the login library; this only decides when it arrives):
     - **Nothing can sign in until the login task.** Better Auth's value is
       its sign-in flows: SMS codes, the admin's passkey. Installed now, it
       would be a login library with every login path unused.
     - **Its schema would set the shape of personal data early.** Its
       core user and session tables (recalled, not checked in this session —
       see below) carry profile fields and per-session client details. The
       login task, with the minors rule and the account-takeover threat in
       view, is where the people tables should be designed.
     - **The safety path needs a header from native code.** The location
       SDK uploads heartbeats from native code (`04b-spike-results.md`
       §4.5), which asks for "per-device authentication". An opaque bearer
       credential works with any HTTP client. A device row is also the anchor
       the data model already plans: platform, push token, readiness.
     - **Fewer dependencies** (SEC-06). A large dependency a milestone before
       its first use is surface with no use.
   - **Fallback:** Better Auth's sessions, read through its bearer-token
     plugin, behind the same `DeviceAuthenticator` port. Routes do not change
     either way.
   - **What the login task inherits:**
     - the `users` and `devices` tables (item 7);
     - the port, the middleware and the "every route but health" test
       (SM-01-AC9);
     - the 401 contract.

     It decides:
     - how a credential is issued: after a Better Auth sign-in, creating a
       `devices` row and returning the credential; or by replacing the adapter
       with Better Auth's session lookup, mapped to a device;
     - expiry, rotation and revocation, which the account-takeover threat
       asks for;
     - the new-device notice;
     - adding sign-in to SM-01-AC9's list of public routes, deliberately, in
       the test;
     - whether Better Auth can use our UUID user IDs or needs a mapping.
   - **Not checked in this session**, to be checked by the specs that rely on
     them:
     - Better Auth's table shapes and its bearer plugin (the login task, against
       the version it pins);
     - whether the location SDK's native uploader sends an `Authorization`
       header (its HTTP headers setting), against 5.7.0's type declarations
       (task 2).

6. **Before the login task, nobody can get a credential through the API.**
   - SM-01 adds no route, seed or migration that creates a user, a device or
     a credential.
   - The production adapter has no insert function for them.
   - L3 tests insert rows directly, using the adapter's exported
     `hashCredential` so the hash matches. L6 tests register devices with the
     fake.
   - On staging the migration creates empty tables. The journey route
     therefore answers 401 to everyone, which is what "staging's journey API
     admits nobody else" asks for (SM-01-AC13).
   - Task 8 decides how the canary gets its credential.

7. **The tables: what they hold, and nothing else.**

   | Table | Columns | Constraints |
   |---|---|---|
   | `users` | `id` (UUID), `created_at` (database time) | — |
   | `devices` | `id` (UUID), `user_id`, `credential_hash`, `created_at` (database time) | `user_id` references `users`; `credential_hash` unique, not null |
   | `journeys` | `id` (UUID), `walker_id`, `state`, `started_at` (database time) | `walker_id` references `users`; `state` limited to `JOURNEY_STATES` (an enum or a check); the partial unique index of item 3 |
   | `journey_responders` | `journey_id`, `responder_id` | primary key on both; each references its table |

   **Not stored:** no name, phone number, location, age band, platform, push
   token, IP address or user agent. No end time or end reason either: those
   arrive with the first task that ends a journey. The migration is generated
   by `drizzle-kit` and committed. `deploy.integration.test.ts` already runs
   every migration on staging's PostgreSQL 15, so it covers this one too.

8. **What this task stores, binds and writes: no personal data in the logging
   rule's sense, and none directly identifying at all** (D-068, D-077 item
   14).
   - **Stored and bound as query parameters:** random IDs, a credential's
     hash, state names and database timestamps. None is a location or a phone
     number, so D-077's follow-up — redaction before a task binds either — is
     not triggered here. Task 2, the first task to bind positions, carries it
     (D-090).
   - **Not yet linked to a person.** No user ID is tied to anyone until the
     login task stores phone numbers. From then on a user ID is a
     pseudonymous identifier, and a journey row — who walked, when, and who
     followed — is personal data. That is for the login task's privacy review
     and the DPIA rule.
   - **The credential itself is never bound into a query and never written
     anywhere** (SM-01-AC11). A Drizzle query error can carry its parameters
     into a message (D-077 item 14), and its parameters include the hash.
     That grants nothing: the server hashes whatever it is given, so
     presenting a hash as a credential fails.
   - **No new log line.** D-077 item 14's caveat stands unchanged: Hono's and
     oRPC's own error output does not pass through `redactCredentials`.
   - **D-068's API pool** still has no `error` listener, so an idle
     connection's error exits the API process, which is loud. This task adds
     database work to the API, not to the worker. D-068's "revisit before the
     worker carries journey state" falls to task 3.

9. **Validation** (SEC-07's second half, for the start route):
   - The body is a strict object holding only `responderIds`. An unknown
     field, a `walkerId` included, is a 400, not ignored.
   - `responderIds` is an array of UUIDs with a fixed upper bound,
     `MAX_RESPONDERS = 50`, held as a contract constant. D-009's group is "at
     least 12 people", and Section 4's cost table plans for 12–20. An
     unbounded list is a cheap way to make the server work.
   - Each ID is lower-cased at the contract (review loop 1). PostgreSQL
     returns UUIDs in lower case and the domain compares strings exactly, so
     an existing user named in upper case would otherwise be refused as
     `INVALID_RESPONDER`.
   - An empty array is valid input. It reaches the domain so that SM-02
     refuses it in its own words (`NO_RESPONDER`), not as a generic 400.

10. **No new dependency** (SEC-06). `node:crypto`, Drizzle, zod and oRPC are
    already in `apps/server/package.json`.

11. **Import boundaries** (AR-10). Only `api-process.ts` and tests import the
    new adapters, following D-077's follow-up rule. Nothing enforces that rule
    yet.

## Acceptance criteria

### Starting, and one unended journey per walker (SM-01)

**SM-01-AC1 — A walker with no unended journey and a valid responder starts
one, timed by the database.**
- **Given** a device credential for user W, no unended journey for W, and an
  existing user R ≠ W
- **When** the device sends `POST /v1/journeys` with `{ "responderIds": [R] }`
- **Then** the answer is 201 with `journeyId`, `state: "ACTIVE"` and
  `startedAt`, and the body parses with the contract's response schema
- **And** one journey is stored, with walker W, state `ACTIVE` and exactly the
  responders [R]
- **And** `startedAt` is the injected clock's time: at L6 exactly the fake
  clock's reading, and at L3 between two `select now()` readings taken by the
  test before and after.

**SM-01-AC2 — A walker with an unended journey cannot start another.**
- **Given** W has a journey J in `ACTIVE`, or in `LOST_CONTACT`
- **When** W's device sends a start with any responder list
- **Then** the answer is 409 `ALREADY_ON_A_JOURNEY`, carrying J's ID
- **And** no journey is created, and J and its responders are unchanged.

**SM-01-AC3 — Racing starts leave exactly one unended journey.**
- **Given** W has no unended journey, in a real PostgreSQL
- **When** at least 10 starts for W run at once, on separate connections
- **Then** exactly one journey for W is unended
- **And** every other attempt is refused with `ALREADY_ON_A_JOURNEY`, carrying
  that journey's ID, and none fails with an unhandled error
- **And** this holds on every repetition the test makes (at least 5).

**SM-01-AC4 — An ended journey does not block a new one.**
- **Given** W's only journey is in `ENDED`. Nothing in this task ends a
  journey, so the test puts it there directly: in the store at L3, or as the
  situation at L2.
- **When** W starts a journey with a valid responder
- **Then** a new journey starts as in SM-01-AC1, and the ended one is
  unchanged.

### At least one responder to start (SM-02's start rule)

**SM-01-AC5 — No responder, no journey.**
- **Given** W has no unended journey
- **When** W's device sends `{ "responderIds": [] }`
- **Then** the answer is 422 `NO_RESPONDER`
- **And** no journey row and no responder row exist for W.

**SM-01-AC6 — Every responder must be an existing user other than the
walker; repeats count once.**
- **Given** W has no unended journey
- **When** the list names W, or names an ID that is not an existing user,
  alone or beside valid responders
- **Then** the answer is 422 `INVALID_RESPONDER`, and nothing is stored
- **And when** the list is [R, R] for an existing R ≠ W, the journey starts
  with exactly one responder, R.

**SM-01-AC7 — An unended journey is reported first, whatever the list says.**
- **Given** W has an unended journey J, in either unended state
- **When** W starts with any responder list — empty, naming W, naming unknown
  IDs, with repeats, or valid
- **Then** the outcome is always `ALREADY_ON_A_JOURNEY` with J's ID
- **And** for any list with no unended journey, the outcome is exactly the
  one item 2 of the approach gives, in that order. This is a fast-check
  property over generated lists and situations.

**SM-01-AC8 — A journey never exists without its responders.**
- **Given** a test-only trigger in a real PostgreSQL that makes inserting a
  `journey_responders` row fail
- **When** W starts a journey with a valid responder
- **Then** the answer is 500, not 201
- **And** no `journeys` row exists for W afterwards, so the transaction rolled
  back whole.

### Every request from a known device, and validated (SEC-07)

**SM-01-AC9 — Every route but health refuses a request without a valid
device credential.**
- **Given** the list of routes, read from the contract (not typed out by
  hand), and a public-route list in the test holding only `GET /v1/health`
- **When** each route not on the public list is called with:
  - no `Authorization` header;
  - an empty one;
  - a scheme other than `Bearer`;
  - `Bearer` with nothing after it;
  - a well-formed credential no device has;
  - the credential of a device whose row has been removed
- **Then** each answer is 401, and the body is the same for every one of
  them, so it says nothing about which check failed
- **And** the route's handler never runs: the fake store records no call
- **And** `GET /v1/health` still answers 200 with no credential
- **And** a route added to the contract later is called by this test
  automatically, so it fails unless that route is authenticated or is added
  to the public list in the test on purpose.

**SM-01-AC10 — The walker is always the device's own user, and the body is
checked.**
- **Given** device D of user W, and another existing user V
- **When** D starts a journey
- **Then** the journey's walker is W
- **And** a body with any field besides `responderIds`, `walkerId: V`
  included, is refused with 400 and nothing is stored
- **And** a body whose `responderIds` is missing, is not an array, holds a
  non-UUID, or holds more than `MAX_RESPONDERS` entries is refused with 400
  and nothing is stored.

**SM-01-AC11 — Only a hash is kept, and the credential is never written
anywhere.**
- **Given** a device registered with a synthetic credential C
- **Then** the `devices` row holds `hashCredential(C)`, and no column of any
  table holds C
- **And when** checking C fails because the store rejects, and when a start
  then fails
- **Then** neither the response body nor anything the API writes to stdout or
  stderr during the request contains C.

**SM-01-AC12 — A database failure while checking a credential is a 500,
never a 401.**
- **Given** the authenticator cannot check, because its store rejects
- **When** a device calls a protected route with a valid credential
- **Then** the answer is 500, not 401
- **And** the handler never runs
- **And** the body is not the 401 body.

*Why it matters:* a 401 tells an app its credential is bad. From task 2 on, a
database hiccup answered with 401 could sign a walker out mid-journey, stop
their heartbeats, and turn into a false alarm.

**SM-01-AC13 — Before the login task, nobody can get a credential.**
- **Given** a freshly migrated database, as staging gets on deploy
- **Then** `users`, `devices`, `journeys` and `journey_responders` are empty
- **And** the only public route is `GET /v1/health` (SM-01-AC9's list). A
  route that issued credentials would have to be public, so it cannot be added
  without that test changing.

### The state machine is one total, exhaustive module (AR-04)

**SM-01-AC14 — Every pair of (situation, event) has a tested outcome, and no
input escapes it.**
- **Given** `JOURNEY_STATES` (exactly `ACTIVE`, `LOST_CONTACT`, `ENDED`) and
  `JOURNEY_EVENTS` (exactly `start`)
- **When** the transition test runs
- **Then** for each pair it holds an expectation for, `transition` returns
  exactly that outcome. The pairs are: none, `ACTIVE`, `LOST_CONTACT` and
  `ENDED`, each with `start`. `ENDED` gives the same outcome as none (review
  loop 1)
- **And** a pair the module's lists create but the test has no expectation
  for fails the test, naming the pair
- **And** for any generated situation and start event, `transition` returns
  one of the four outcomes, never throws and never returns `undefined`
  (fast-check)
- **And** typecheck (L1) fails if an event type has no handling in
  `transition`.

**SM-01-AC15 — The database and the module agree on the states.**
- **Given** a freshly migrated database
- **Then** the set of states the `journeys.state` column allows equals
  `JOURNEY_STATES`
- **And** inserting a journey with a state outside it is refused by the
  database.

### The contract (AR-07, D-030)

**SM-01-AC16 — The contract describes the route, its refusals and its
authentication.**
- **Given** the generated OpenAPI document
- **Then** it has `POST /journeys` under the `/v1` server, whose responses
  include 201, 400, 401, 409 and 422
- **And** it declares a bearer security scheme, required on `POST /journeys`
  and absent from `GET /health`
- **And** the committed `packages/contracts/openapi.json` equals what the
  contract generates. That is the existing test, kept.
- **And** `pnpm run api:diff` is run. With no released version in
  `packages/contracts/released/` it reports that it compared nothing, which
  is recorded in the pull request as "not compared", not as "passed".

## Contract changes

Additive only. `packages/contracts/released/` is empty, so nothing on a phone
can break, and nothing is added there (release-engineer's alone).

- **`POST /v1/journeys`**, contract path `/journeys`. Its route summary
  states that it needs a device credential and that a walker can have only
  one unended journey.
  - **Request** (strict): `{ responderIds: string[] }`. Each entry is a UUID;
    at most `MAX_RESPONDERS` (50); may be empty, and the domain then refuses
    it.
  - **201:** `{ journeyId: UUID, state: "ACTIVE", startedAt: RFC 3339 }`.
    `startedAt` is described as database time.
  - **400 `BAD_REQUEST`:** the body fails the schema (SM-01-AC10).
  - **401 `UNAUTHORIZED`:** no valid device credential. The body is the same
    for every cause.
  - **409 `ALREADY_ON_A_JOURNEY`:** with `{ journeyId }`, the caller's own
    unended journey. Carrying it lets an app whose first answer was lost
    adopt the journey rather than leave one running that it does not know
    about.
  - **422 `INVALID_RESPONDER`:** names the walker or an ID that is not a user.
  - **422 `NO_RESPONDER`:** an empty list (SM-02).
  - **500:** unchanged in shape. The internal error does not reach the caller
    (SEC-03, as tested today).
- **Security:** a bearer scheme in `components.securitySchemes`, required on
  this route and absent from `/health`. If oRPC's generator cannot express
  either, the pull request says so plainly. `openapi.json` is never edited by
  hand.
- **`/v1/health`** is unchanged, and stays public.
- **Exports from `@trygghverdag/contracts`:** the schemas, their types,
  `MAX_RESPONDERS`, and the error-code names. The app (M3) will read them from
  here, never from a copy.

## Risks and failure modes

- **[F6](../plan/03-safety-reliability-security.md#failure-modes), a missed
  alert.** A journey that starts with nobody to alert fails silently, later
  and at the worst moment.
  - **Guarded by:**
    - SM-02's start rule (AC5);
    - responders that must be real users other than the walker (AC6);
    - a journey and its responders written together or not at all (AC8).
  - **Not guarded yet:** a responder who exists but cannot be reached — no
    device, no push token — still counts. Readiness is the responder-setup
    story's (M3). Until then task 3 must make a push with no target fail
    loudly, not count it as sent.
- **[F7](../plan/03-safety-reliability-security.md#failure-modes), the server
  or watchdog down.**
  - The API now queries the database on every protected request. A database
    that cannot answer gives a 500 (AC8, AC12), never a 401 and never a
    half-started journey.
  - The health endpoint is unchanged and public, so INF-08's monitors see
    what they saw before.
  - D-068's API pool still exits on an idle connection's error. That is loud,
    and unchanged by this task.
- **[F8](../plan/03-safety-reliability-security.md#failure-modes), a bad
  release breaks alerts.**
  - A later task that adds a state or event without tests fails L1 and L2
    (AC14), and one that adds a state on only one side fails L3 (AC15).
  - A route shipped without authentication fails AC9.
  - A change to the start rule's order fails AC7's property.
  - Mutation on `domain/` keeps the tests honest (D-036).
- **[F2](../plan/03-safety-reliability-security.md#failure-modes), no
  coverage.** A start whose answer is lost in a tunnel is retried. The retry
  gets 409 with the journey's ID (AC2, AC7), so the app can adopt the journey.
  Without that, the server would watch a journey the phone does not know
  about, and from task 3 that becomes a false alarm. Full idempotency, an ID
  on every event, is the duplicate-event rule's (task 2).
- **[F10](../plan/03-safety-reliability-security.md#failure-modes), someone
  else on an unlocked phone.** Per-device authentication does not help: the
  phone is the device. This stays a known limitation.
- **F1, F3, F4, F5 and F9 are not touched.** They concern the phone and
  positions.
- **Two starts racing.** The database decides (AC3), not process memory.
- **A leaked credential is a whole device.** It has no expiry or revocation
  until the login task.
  - Today none exists outside tests.
  - It is kept only as a hash (SEC-03, AC11), and never logged (AC11).
  - Task 8's canary credential is the first real one, and its handling is
    task 8's.
- **Nothing in M2 ends a journey until task 4 or 7.** A test walker therefore
  gets one journey per database, and the canary (task 8) will need an end.
  This is a note for task 8, not a defect here.
- **The fake can drift from the adapter.** The shared behaviour suite (Test
  plan) holds them together.
- **A coverage report that reads as done.** The rows turn 🟢 while three
  halves remain (see "How this spec names requirements").

## Questions for the owner

**None that block SM-01.** One gap is recorded for M4 rather than asked now:

1. **How long are journey records kept?**
   - The retention rule (privacy table, 4th row) sets times for three things:
     precise positions (24 hours after a journey ends), alert records (30
     days), and account data (when a member leaves).
   - It sets none for the journey record itself: who walked, when, in which
     state, and who followed. The 24-hour rule's "retention counts from the
     end" does not say what is deleted then.
   - This task creates those rows, but none can end before task 4, and
     before the login task none is linked to a person. So nothing personal
     waits on the answer in M2.
   - **Recommendation:** delete a journey's row and its responder rows
     together with its alert records, 30 days after it ends. Record the
     answer as a decision in M4, and write it into the DPIA.
